# Архитектура

> Версия 0.1 · 23.10.2026. Решения — в [ADR](adr/). На ступени 0 строится только движок и CLI; сервисная
> часть описана как цель и переносится из `second-key` на ступени 2.

## Контекст

```
   CLI (ступень 0)          MCP для агента заказчика (0.13)          веб и плагин САПР (ступень 2+)
         │                               │                                       │
         └───────────────────────────────┼───────────────────────────────────────┘
                                         ▼
                      движок zerocycle (без IO): пакет → находки
        приём → опись → основные надписи → факты → правила пакетов → отчёт и решения
                                         │
        индекс норм («Стройкомплекс.РФ», позже РК) · LLM через llm.run() — извлечение и тексты
```

## Принципы

1. **Движок без IO.** Чистые функции над моделью пакета: тесты и бенчмарк работают на данных, без БД и сети —
   как `secondkey.engine`.
2. **Без якоря нет факта, без факта нет находки.** Якорь — файл (sha256), страница и рамка в пунктах PDF;
   для XML — путь к элементу; для xlsx — ячейка; для IFC — GUID.
3. **Правила детерминированы.** LLM работает только в извлечении (типизированный ответ с цитатой и якорем),
   классификации и текстах; итоговых чисел и вердикта «нарушено» не выдаёт.
4. **Честные статусы:** нарушено, норма, проверить вручную, проверить невозможно. Последний лучше догадки.
5. **Воспроизводимость:** прогон записывает версии движка, пакетов правил, индекса норм, моделей и промптов.
6. **Юрисдикция — подключаемый пакет** поверх общего ядра ([ADR 0003](adr/0003-jurisdiction-packs.md)).
7. **Документы — данные, а не инструкции:** текст пакета никогда не исполняется как указание модели;
   сенсоры инъекций — из procdesk.

## Поток проверки

| Стадия | Что делает | Выход |
|---|---|---|
| 1. Приём | папка, zip или ПДЭ; sha256 файлов; тип по содержимому, а не по расширению | `Package.files` |
| 2. Опись | документ → раздел, подраздел, часть, книга; обозначение; из info.xml, если он есть | `Document` |
| 3. Основные надписи | поиск по геометрии форм 3–6 у правого нижнего угла внутренней рамки; графы → поля | `TitleBlock` каждой страницы |
| 4. Факты | ТЭП, наименования объекта, обозначения, ссылки на нормы, ведомости и содержания как таблицы | `Fact` с якорем |
| 5. Нормализация | единицы (м², м³, этажи), обозначения, ссылки на нормы → записи индекса | канонические значения |
| 6. Правила | пакеты `core` → `spds` → юрисдикция → организация; применимость по виду объекта, стадии, дате | `Finding` |
| 7. Отчёт | категории экспертизы, доказательства с рендером фрагмента, покрытие правил, решения | JSON, HTML |

## Модель данных ядра

| Тип | Ключевые поля |
|---|---|
| `Package` | id; юрисдикция; вид объекта (производственный, непроизводственный, линейный, особый состав); вид работ (строительство, реконструкция, капремонт); стадия (П/Р); дата подачи; базовое обозначение; файлы |
| `Document` | файл; вид (текстовый, графический, таблица, XML, модель); раздел, подраздел, часть, книга; обозначение; наименование; листы |
| `Page` | номер; размер и формат по ГОСТ 2.301; ориентация; слова с координатами; `TitleBlock` |
| `TitleBlock` | форма (3–6); графы 1–27 как поля с рамками; уверенность разбора |
| `Fact` | вид (`tep.total_area`, `object.name`, `designation`, `normref` …); значение; единица; якорь; извлекатель; уверенность |
| `Anchor` | sha256 файла; страница; рамка (x0, y0, x1, y1 в пт) / путь XML / ячейка / GUID; цитата |
| `NormRef` | как написано в тексте → документ индекса, редакция, статус, даты, пункт |
| `Rule` | id; версия; пакет; семейство; вид; тяжесть; применимость; основания; фикстуры; статус рецензии |
| `Finding` | правило; статус; факты; якоря; сравниваемые значения; основание; сообщение; уверенность |
| `Decision` | находка; кто; принято или отклонено; причина |
| `Run` | версии движка, пакетов, индекса, моделей и промптов; время; стоимость |

На ступенях 0–1 прогон пишет JSON рядом с пакетом (`var/runs/…`). Postgres + pgvector и S3 — со ступени 2.

## LLM

- **Где:** извлечение ТЭП и пунктов содержания ПЗ в типизированную схему с обязательной цитатой; классификация
  замечаний (ступень 1); тексты находок и черновики ответов (ступень 2).
- **Как:** `llm.run(module, Inputs)` — модуль промпта (prompt.toml, Jinja2, pydantic), OpenAI-совместимый
  провайдер; по умолчанию — дешёвая модель; матрица моделей — часть бенчмарка; локальная модель подключается
  тем же интерфейсом.
- **Без ключа** движок работает: детерминированные правила от LLM не зависят, а правила, которым нужен факт
  от LLM, возвращают «проверить невозможно».

## Индекс норм и grounding

Индекс собирается из реестра НТД и реестра требований «Стройкомплекс.РФ» (`bim-data/datasets/stroykompleks/`):
документ, вид, статус, даты, замены, пункты-требования. Ссылка в тексте пакета разбирается и сверяется с
индексом на дату подачи. Grounding-гейт отчёта: каждое число — из фактов, каждая ссылка — из индекса,
каждая цитата — из текста по якорю; иначе находка не выходит ([ADR 0004](adr/0004-rules-evidence-grounding.md)).

## Развёртывание

| Ступень | Как |
|---|---|
| 0–1 | CLI локально; пакеты партнёров не покидают машину; внешний LLM — только с согласия владельца пакета |
| 2 | single-host docker compose из second-key: api, worker, Postgres, Redis, S3, web |
| 3+ | контур заказчика: тот же compose, локальная модель (vLLM), без внешних вызовов |

## Безопасность и данные

- Пакеты партнёров хранятся только локально и по договорённости; в корпус попадают обезличенными (подписи, ФИО).
- Внешние LLM — только с согласия владельца пакета; иначе локальная модель или без LLM.
- Тексты ГОСТ и СП не показываются целиком — только ссылки и пункты реестра.
