# Доказательства и результат

Выходной JSON строго соответствует [схеме отчёта](report.schema.json): только `findings` (массив) и `summary` (строка). Каждый finding содержит ровно шесть обязательных полей из таблицы ниже; дополнительные поля запрещены на обоих уровнях. Верни один JSON-объект без Markdown-ограждений и текста вне него. Все строки на русском, пути внутри пакета с прямыми `/`, точные имена файлов без исправления регистра и орфографии. Не переносить ошибки в именах в другой путь.

## Поля одного finding

| Поле | Значение |
|---|---|
| `category` | Ровно одно значение: `комплектность`, `оформление`, `увязка`, `нормы и ссылки на них`, `расчёты`, `смета`, `формат подачи`. Выбирай по существу подтверждённого замечания; наличие категории не расширяет доступную нормативную базу. |
| `document` | Путь внутри `package/` к первичному дефектному документу, без префикса `package/`, например `04 КР/2026-07-КР1.pdf`. Для подтверждённо отсутствующего документа — строго `package/`. Нормативный источник здесь не ставить. |
| `page` | Физическая страница PDF от **1**, не номер листа в штампе/содержании. `null` для документа целиком и всех не-PDF: Excel, Word, изображения. Если PDF-страница дефекта известна, укажи её. |
| `status` | Только `нарушение` или `проверить вручную`. |
| `description` | Конкретный наблюдаемый дефект, его масштаб и доказательства: фактические цитаты, точные локаторы (страницы PDF, листы/ячейки Excel, части/абзацы Word, графы, кадры изображений). Для отсутствия — какой именно документ отсутствует, краткий журнал проверки всего релевантного пакета и ссылка на запись в `review_work/completeness_matrix.md`. Для расхождения — обе исходные записи с единицами, путями и локаторами, уточнение версии/части объекта; для ручной проверки — факт, неопределённость и что именно должен решить человек. |
| `basis` | Документ нормы, точный пункт/подпункт/приложение и короткая проверенная цитата, относящаяся к факту. Для АГСК — издание, раздел, PDF-страница/строка и точное обозначение записи; если номера пункта нет — так и написать. Допустим второй нормативный источник, если он нужен. |

Доказательства из пакета включай текстом в `description`, нормативные цитаты — в `basis`; отдельные поля `evidence`, `locator`, `quote` не добавляй. Для визуального дефекта дай точное описание увиденного вместо текстовой цитаты; не выдавай его за OCR. Черновые рендеры могут быть упомянуты в `description`, но `document` остаётся исходным файлом пакета, `page` — исходной страницей PDF. Инвентарь и команды скриптов используют пути с `package/`; в полях и текстовых ссылках итогового отчёта указывай пути внутри пакета без этого префикса (кроме специального значения `package/` для отсутствующего документа).

## Порог доказательства

«Нарушение» требует совместно: применимая точная норма; подтверждённое условие; доказанный факт дефекта; достоверный локатор. Для отсутствия нужен обзор всех возможных мест нахождения документа. Не подставляй вымышленные даты, числа, номера пунктов, причины или последствия. Не называй весь проект несоответствующим из-за одного установленного листа.

«Проверить вручную» требует факта, найденного в пакете, и конкретного вопроса человеку, например спорная читаемая подпись на данном листе или применение старой нормы в проекте с неясной датой. Сошлись на точное доступное требование и явно назови неопределённость. Этот статус не доказывает нарушение.

Не нашли текст СН; неизвестен статус ГОСТ; файл не открывается; OCR отсутствует; инженерный расчёт недоступен; обязательность раздела неизвестна — это ограничения в тексте `summary`. Не создавать для каждого такого ограничения finding. Не привязывать произвольное требование к общему пункту ГОСТ 3.1/4.1.2. Подтверждённые расхождения ТЭП без доступной точной нормы опиши в строке `summary`, с обеими ссылками и без статуса нарушения.

Не повторяй один дефект в нескольких пунктах с одинаковыми доказательствами. Если несколько разных страниц подтверждают системный дефект, перечисли все проверенные локаторы, но не расширяй вывод на непроверенные листы.

## Summary

`summary` — одна строка с содержательным текстом, не объект, не массив и не сериализованный JSON. В ней опиши как минимум:

- Установленный вид работ/стадию/финансирование, выбранные приложения и неизвестные условия.
- Что фактически просмотрено (файлы, PDF-страницы, Excel-листы, Word-части, изображения), что сделано только поиском текста и где была выборка. Число извлечённых страниц не равно числу визуально проверенных.
- Точные непроверенные файлы/страницы и причины; непроверенные вложения/архивы; отсутствие текстов СН РК 1.02-03-2022 и п. 15 Правил; пределы ГОСТ и АГСК, июнь 2025; неизвестные условия применимости; ограничения расчётов/кешей Excel и Word-вёрстки. Не перечисляй ошибки, которых фактически не было.
- Найденные по файлам расхождения, которые нельзя оформить как нормативное нарушение из-за отсутствия точного основания; оба значения/названия с единицами, путями и локаторами. Если таких нет — так и напиши.
- Краткий вывод в пределах охвата. Не «пакет полностью соответствует всем нормам» при неполной базе/покрытии.

Допустим пустой `findings`. Рабочая структура без вымышленных замечаний:

```json
{
  "findings": [],
  "summary": "Заполняется по фактически проведённой проверке: что проверено, что проверить не удалось и почему; подтверждённые расхождения без точного нормативного основания — с обоими значениями и локаторами."
}
```

Перед ответом: сверить каждый факт с исходной страницей/ячейкой; не перепутать номер страницы источника с номером страницы пакета; проверить пункт и оговорки; убрать предположения/дубли; выполнить `check_report.py`. Он проверяет поля, типы, категории, статусы, отсутствие дополнительных полей и основной путь/страницу по инвентарю; дополнительно требует непустые `description` и `basis`. Текстовые доказательства, локаторы внутри `description`/`summary` и нормативные выводы проверяй самостоятельно.
