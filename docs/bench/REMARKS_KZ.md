# Замечания экспертизы РК: замер гипотезы H1

> 26.10.2026 · PLAN, шаг 0.11b. Корпус — заключения экспертизы из вложений закупок строительных работ на
> goszakup.gov.kz. Код — `src/zerocycle/remarks/`, разметка — [`data/remarks_kz_labels.tsv`](data/remarks_kz_labels.tsv),
> перечень заключений — [`data/remarks_kz_conclusions.tsv`](data/remarks_kz_conclusions.tsv). Сами PDF — в `var/`
> (вне git).

## Вопрос и ответ

Гипотеза H1 ([STRATEGY, § 13](../product/STRATEGY.md#13-гипотезы-и-проверка)): формальные дефекты — заметная доля
реальных замечаний; порог — не меньше 25% замечаний в категориях «комплектность, оформление, увязка, ссылки».
Писем замечаний без партнёра нет, но в заключениях экспертизы РК есть их след: подраздел «Дополнения и изменения,
внесённые в рабочий проект в процессе экспертизы» — что проектировщик исправил по замечаниям, по разделам, пунктами.

**H1 на данных РК подтверждается с запасом: формальные — 62% пунктов, 95-процентный интервал 57–67%.** Самый
осторожный из вариантов замера — 51%, вдвое выше порога.

|---|---|---|

| Среднее долей по заключениям (с 3 и более пунктами) | 63,8% | — |
| Одинаковые тексты одной экспертной организации — один раз | 60,8% (465 из 765) | 55,6–66,2% |
| Организация как единица: бутстреп по 30 организациям | 61,9% | 56,0–67,5% |
| Среднее долей по организациям — у каждой один голос | 51,0% | — |

| Верхняя граница: плюс «состав изображения» | 70,6% | — |

Формальные категории — комплектность, оформление, увязка, ссылки на нормы и формат подачи (последний добавляет 1%).

## Данные

- **Закупки.** Поиск по словам «строительство», «капитальный ремонт», «реконструкция»: завершённые закупки
  работ дороже 150 млн ₸, первая страница выдачи. Получилось 150 объявлений. У 74 из них в технической
  спецификации есть файлы с «заключением» в имени — их и скачали (`scripts/goszakup_kz_psd.py fetch --only`).
- **Заключения.** 81 файл, из них 80 разных по содержимому. Найдено 4 копии: один и тот же список изменений в заключениях одной
  организации по однотипным объектам — у ЮЖГОРЭКСПЕРТИЗЫ «ФОК Талап» = «ФОК Кенгир», у Pro Expertize KZ три
  школы, у ЮКПроектЭкспертизы два двора. Копии считаются один раз. Ещё 4 файла — не заключения по ПСД
  (экологическая экспертиза, техническое заключение, два письма).
- **Подраздел есть не у всех.** Из 72 заключений по ПСД:
  - у 49 подраздел есть, в нём есть пункты;
  - у 2 написано, что изменения не вносились;
  - у 21 подраздела нет: 15 из них — заключения РГП «Госэкспертиза», у которой в форме заключения нет списка
    изменений, только ТЭП «заявленные / рекомендуемые к утверждению»; 6 — частные экспертизы с другой формой.

  Замер, таким образом, — по частным экспертным организациям.
- **Пункты.** 893 пункта, из них 868 разных текстов; 31 экспертная организация. На заключение — от 1 до 77
  пунктов, медиана 12. По годам выдачи: 34 заключения 2026 года, 8 — 2025, 7 — 2018–2024.

## Как считали

1. **Разбор** (`remarks/conclusion.py`):
   - текст страниц (pdfplumber), колонтитулы убираются по повторяемости на страницах;
   - заголовок подраздела в четырёх вариантах, занимает до трёх строк; из оглавления берётся тот кандидат,
     под которым нашлись пункты;
   - конец подраздела — следующий подраздел, глава «ВЫВОДЫ», «Таблица №…» или «После внесения изменений…»;
   - группы — заголовки разделов проекта;
   - пункты — «1.», «1)», «7.2.1.», маркеры; без нумерации — по предложениям и коротким последним строкам абзацев;
   - «таблицей 4 п.» и «2.4.1 СН РК…» на следующей строке — продолжение пункта, а не новый пункт.

   Реальные варианты закреплены синтетическими регрессиями в `tests/test_remarks.py`.
2. **Кодбук** (`remarks/classify.py`) — 9 категорий, таблица ниже. Упорядоченные правила-выражения дают черновик
   категории для каждого пункта.
3. **Разметка.** Каждый из 893 пунктов просмотрен, несогласные с правилами исправлены — 277 пунктов. Правила
   совпали с разметкой в 69% случаев. Это метрика кодбука как автоматического классификатора, а не точность
   замера. Разметку делал Claude по кодбуку; спорные решения записаны в колонке `note`.
4. **Замер** (`remarks/measure.py`). Пункты одного заключения не независимы: один эксперт, одна манера. Поэтому
   интервал — перцентильный бутстреп с перевыборкой заключений, 4 000 повторов. Варианты в таблице выше
   проверяют, не решают ли за всех длинные списки, копии и шаблоны одной организации.

Пограничные решения кодбука (одинаково во всех пунктах):

- **Расчёты.** Расчёта не было, его представили — комплектность. Расчёт исправили — расчёты.
- **Листы и элементы чертежа.** Не было листа или схемы — комплектность. На листе не хватало элемента —
  состав изображения.
- **Спецификация** относится к разным категориям в зависимости от того, что в ней исправили:
  - количества — расчёты;
  - выбор оборудования и материалов — решения;
  - форма (графы, коды АГСК-3, марки и стандарты для идентификации) — оформление;
  - приведена в соответствие с планами или изменениями — увязка;
  - «откорректирована» без подробностей — без содержания.
- **Смета.** Документы сметы представлены — комплектность; формат файлов — формат подачи; объёмы, цены и следование
  за изменениями проекта — смета.
- **ТЭП и задание.** Исправленные или пересчитанные ТЭП — увязка. Задание на проектирование дополнено под
  проект — увязка; реквизиты задания (дата, номер, форма) — оформление.
- **Согласования.** «Согласовано со смежными разделами» — увязка; штамп или графа согласования — оформление;
  согласование с заказчиком или ведомством — комплектность.
- **Несколько правок в одном пункте** — по первой упомянутой.

## Что это значит для продукта

1. **Первое правило пакета `kz` — комплектность.** Нужен перечень обязательных документов и расчётов по
   СН РК 1.02-03-2022 и по разделам: ИРД и согласования (в 27 заключениях из 49), расчёты (18), листы и схемы
   (20), сведения в ПЗ (20). Это та же семья правил, что ПП 87 для `ru`: движок общий, перечни разные.
2. **Оформление ловится тем, что уже есть.** Основная надпись, подписи и титульные листы (14 заключений) —
   это опись штампов из шагов 0.3 и 0.11. Общие данные и ведомости (19) — пакет `spds`, шаг 0.6.
3. **В РК действует другая редакция СПДС.** Эксперты ссылаются на ГОСТ 21.101-97 (в 14 заключениях); на
   ГОСТ Р 21.101-2020 — ни разу. Отраслевые стандарты тоже межгосударственные: ГОСТ 21.110-2013, 21.601-2011,
   21.602-2016, 21.508-93. Значит, у пакета `spds` должна быть редакция стандарта как измерение: 97 — РК,
   2020 — РФ. Иначе правила ГОСТ Р будут давать ложные тревоги на казахстанских пакетах.
4. **Свои справочники РК.**
   - Ссылки на нормы проверяются по АГСК-1 — ежегодному перечню действующих нормативных документов, аналогу
     реестра «Стройкомплекс.РФ».
   - Коды в спецификациях — по классификатору АГСК-3 (10 заключений), это требование СН РК 1.02-03-2022, п. 5.13.
   - Смета — по НДЦС РК 8.01-08-2022, исходные данные — в KENML.

   Оба справочника надо добавить в `bim-data/`.
5. **Смета — отдельный контур.** На неё приходится 10% пунктов, и это в основном содержание: объёмы, расценки.
   Формальная часть сметы — состав документов и формат подачи — в клин v1 входит.
6. **Экспертиза ловит не всё.** Увязку «наименование объекта ↔ АПЗ» эксперты исправляли всего 4 раза в 3
   заключениях. Между тем в пакете Тауыш с положительным заключением в штампах осталось чужое место
   строительства ([REAL_KZ](REAL_KZ.md)). Предпроверка нужна не только для того, чтобы пройти экспертизу.
7. **Редакции норм путают и сами эксперты.** В заключениях 2025–2026 годов СН РК 1.02-03 цитируют по-разному:
   8 заключений ссылаются на редакцию 2011 года, 7 — на редакцию 2022 года. Надо проверить, заменена ли
   редакция 2011 года и есть ли переходный период. Если заменена, устаревшие ссылки есть и в самих заключениях.
   В любом случае проверке ссылок нужна таблица замен и для РК.

## Ограничения

1. **Мерили след замечаний, а не сами замечания.**
   - В подразделе перечислено, что изменили. Одно замечание может дать несколько пунктов, и наоборот.
   - Эксперты пишут по-разному: от одной строки до 77 пунктов.
   - Формулировки вида «представлен …» могут смещать долю в сторону комплектности: «представлен расчёт» написать
     проще, чем описать изменённое решение.
2. **Отбор.**
   - Только частные экспертизы с этим подразделом: у «Госэкспертизы» подраздела нет.
   - Только положительные заключения и только объекты, которые дошли до закупки СМР.
   - Первая страница поисковой выдачи — свежие закупки; поэтому 2026 год преобладает.
3. **Один аннотатор.** Разметку делал Claude по кодбуку; согласие со вторым аннотатором не измерено. Нужна проверка
   практиком (PLAN, F3) хотя бы на 100 случайных пунктах — с оценкой каппы.
4. **Граница «формальное / содержательное» в нескольких местах условна:** состав изображения, коды АГСК-3,
   «расчёта не было» против «расчёт неверен». Решения записаны в кодбуке и в заметках к пунктам. Варианты замера
   показывают, что вывод от этих решений не зависит.
5. **«Формальное» — не то же самое, что «проверяется в v1».** Чтобы найти отсутствующий гидравлический расчёт,
   нужен перечень обязательных расчётов раздела. Чтобы проверить ТЭП, нужно извлечь их из чертежей. Долю,
   которую закроет v1, предстоит мерить отдельно — по разметке типов, когда появятся правила.
6. **Только РК.** Для РФ нужен свой замер: письма замечаний партнёров (ступень 1) или публичные перечни типовых
   ошибок.

## Как воспроизвести

```powershell
# кандидаты: 150 завершённых закупок СМР и файлы их техспецификаций (выдача меняется со временем —
# набор этого замера закреплён в data/remarks_kz_conclusions.tsv)
python -I -X utf8 scripts/goszakup_kz_psd.py list var/real/goszakup_kz/_list.json --pages 1
python -I -X utf8 scripts/goszakup_kz_psd.py fetch var/real/goszakup_kz --from-list var/real/goszakup_kz/_list.json --only "заключ|қорытынд" --workers 4
# разбор, разметка и замер
uv run python -m zerocycle remarks var/real/goszakup_kz --cache var/cache/remarks_text --labels docs/bench/data/remarks_kz_labels.tsv
# черновик разметки для нового корпуса: категории по правилам, прежняя разметка сохраняется по ключу
uv run python -m zerocycle remarks <папка> --labels docs/bench/data/remarks_kz_labels.tsv --export-labels draft.tsv
```

Ключ пункта — хеш заключения и текста пункта. Он не зависит от нумерации и от версии кодбука, поэтому разметка
переносится на новые прогоны разбора.
