# ADR 0001 — Отдельный репозиторий на общем ядре

Статус: принято · 23.10.2026

## Контекст

В `development_challenge` уже есть «Второй ключ» (`second-key/` — контроль цен закупок для собственника
стройкомпании в КР), замороженный стенд procdesk и база данных `bim-data/`. Новый продукт — проверка пакета
проектной документации — это другой покупатель (проектное бюро, заказчик), другие юрисдикции (РФ, затем РК),
другие документы (тома PDF, ПДЭ, XML, позже IFC) и другое развёртывание, вплоть до контура заказчика.
Владелец развивает оба продукта параллельно.

## Решение

1. `zero-cycle/` — отдельный git-репозиторий в корне `development_challenge`; внешний репозиторий его игнорирует.
2. Общий код не подключается зависимостью: нужные части **копируются** из second-key и procdesk — так же,
   как second-key забрал движок из procdesk (его ADR 0001).
3. Платформа (API, очередь, S3, роли, веб) не переносится до ступени 2: на ступени 0 нужны только движок и CLI.
4. Общий пакет ядра выделяется, когда выполнены оба условия: один и тот же модуль второй раз одинаково
   правится в двух репозиториях, и у обоих продуктов есть хотя бы по одному реальному клиенту.

## Почему

- Модели данных не обобщаются: находка «Второго ключа» — деньги по строкам закупки, здесь — пункт нормы по
  листу или элементу модели. Общая таблица находок наполовину состояла бы из пустых колонок.
- Тяжёлые зависимости и лицензии (разбор PDF, рендер, позже IfcOpenShell) не должны попадать в образ second-key.
- Разная зрелость и скорость: связка заставила бы эксперименты одного продукта ломать другой.
- Отдельный репозиторий проще показать партнёру, депонировать или поставить в контур заказчика.

## Последствия

- Улучшения скопированных модулей (`llm.run()`, MCP-обвязка) переносятся вручную; расхождения отмечаются
  в журнале PLAN.md.
- Общее у продуктов — философия независимой проверки перед необратимым шагом и инженерные принципы,
  а не кодовая база.
